# Working style for this project

- Keep step-by-step narration minimal. Don't describe each tool call or intermediate action in prose.
- Only report real checkpoints: what was done, what the result was, and any bugs/blockers found. E.g. "Fixed X — tested, works" or "Found bug: Y, fixing now."
- Skip restating plans already agreed on before executing them.
- Subagents are expensive here (measured ~127K tokens for one medium Kanban rewrite) — they start cold and re-derive context the main session already has, plus each one boots its own dev server for live verification. Reserve them for genuinely large, independent chunks of work. For medium-sized tasks, do them directly in the main session instead — it already has the context, no re-deriving needed.
- If a set of remaining tasks is genuinely large AND independent (separate files/areas, no shared in-flight edits), split it across parallel subagents to execute concurrently — but ask explicit permission first before dispatching them. Use model "sonnet" (Sonnet 5) for these subagents. Don't do this when the tasks touch the same files you're currently editing yourself (real conflict risk) or when a task is small/medium enough that doing it directly costs less than spinning up an agent.
- Every subagent prompt must tell it to check for `graphify-out/graph.json` first and query it (`graphify query "<question>"`) for orientation before grepping/reading broadly — this is the main lever for cutting a subagent's cold-start token cost. If no graph exists yet, have it build one (`graphify <path>`) before diving into unrelated exploration. After a subagent's work is merged, run `graphify <path> --update` in the main session so the next subagent's graph is current — a stale graph trusted blindly is worse than none.
- Never leave finished work sitting uncommitted. After any edit that isn't itself the very first step of a longer plan, commit it (locally is enough — push isn't required every time) before moving on to the next thing. Session/usage-limit interruptions can happen without warning and mid-turn edits are not guaranteed to survive a reset — an uncommitted change is work that can simply vanish. This applies to my own direct edits and to merging a subagent's completed work alike.
